# AI Development Rules

## Purpose

This repository is the reference source for analyzing the current WordPress implementation and preparing implementation instructions for human developers.

## Development Flow

1. Development is performed manually by a human on the staging environment.
2. Changes are made through WordPress admin or FTP/SFTP.
3. GitHub is used as a reference mirror of the staging source.
4. Do not propose GitHub-to-staging or GitHub-to-production automatic deployment unless explicitly requested.
5. Production deployment uses the existing scheduled deployment process.

## Analysis Rules

Before proposing any implementation:

1. Search the existing code first.
2. Identify all related PHP, HTML, JavaScript and CSS files.
3. Check whether an existing function, class, component, shortcode, widget or script can be reused.
4. Prefer reuse over creating duplicate implementations.
5. Identify the exact files that may need to be modified.
6. Consider both desktop and mobile behavior.
7. Check whether the change may affect existing GA4, GTM or CTA tracking.
8. Avoid modifying unrelated functionality.
9. Ignore backup files such as files containing .___bak in the filename.
10. Treat the current non-backup file as the active implementation.

## WordPress Specific Rules

When analyzing the implementation, also check:

- functions.php
- header.php
- header-magazine.php
- footer.php
- footer-magazine.php
- single.php
- page templates
- template-parts/
- css/
- css_magazine/
- js/
- widget areas
- shortcodes
- wp_enqueue_script / wp_enqueue_style definitions

## CTA / Tracking Rules

When the requested change involves a CTA or navigation link:

1. Identify where the CTA is rendered.
2. Check whether it is generated by PHP, shortcode or WordPress widget.
3. Identify related CSS and JavaScript.
4. Check whether href, class, id or DOM structure changes may affect GTM triggers.
5. If the actual widget content or GTM configuration is not present in GitHub, explicitly state that WordPress admin or GTM must also be checked.

## Required Output

When an implementation is requested, provide the following:

1. Current implementation summary
2. Related files
3. Existing functionality that can be reused
4. Recommended implementation approach
5. Files to modify
6. Exact modification instructions
7. PHP / HTML changes
8. JavaScript changes
9. CSS changes
10. WordPress admin changes, if applicable
11. Potential side effects
12. Desktop test checklist
13. Mobile test checklist
14. GA4 / GTM test checklist, if applicable

## Deployment

The human developer performs changes on the staging environment.

Production deployment is outside the scope of this repository.

Do not change the existing staging-to-production scheduled deployment process unless explicitly requested.
